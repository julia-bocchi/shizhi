# 前后端接口合约文档

## 1. 文档目标

本文用于明确本项目健康管理系统前后端之间的接口合约，作为以下场景的统一依据：

1. HarmonyOS 前端调用后端接口
2. Spring Boot 后端实现接口
3. 前后端联调与验收

## 2. 系统角色与适用范围

### 2.1 接口提供方

- 业务后端服务：`Spring Boot`
- 数据持久化：`MySQL`

### 2.2 接口消费方

- HarmonyOS 应用前端
- 主要调用入口位于 `entry/src/main/ets/utils/ApiService.ets`

### 2.3 本文覆盖模块

1. 账号注册与登录
2. 用户资料
3. 体重记录
4. 食物选项与饮食计划
5. 训练类型与训练模板
6. 训练计划
7. 训练记录与训练汇总

### 2.4 不在本文合约范围内的能力

AI 助手与智能推荐当前默认直连第三方大模型接口，不经过本业务后端，因此以下接口不纳入正式业务合约：

- `POST /api/v1/ai-assistant/chat`

## 3. 合约总则

### 3.1 协议与数据格式

- 传输协议：`HTTP/HTTPS`
- 数据格式：`application/json`
- 字符编码：`UTF-8`

### 3.2 Base URL

本项目存在两个典型联调地址：

1. 本地 mock 联调地址

`http://127.0.0.1:3000/api/v1`

2. 当前前端默认远程地址

`https://diffusion-dose-playing.ngrok-free.dev/api/v1`

说明：

- 前端会从本地已保存配置中读取联调地址
- 若本地未配置，则回退到当前源码中的默认地址
- 后端正式部署时，只需保证路径前缀与本文一致即可

### 3.3 统一请求头

除注册、登录接口外，其余业务接口默认携带以下请求头：

```http
Authorization: Bearer <token>
X-User-Id: <userId>
Content-Type: application/json
Accept: application/json, text/plain, */*
```

字段约定：

| 请求头          | 类型   | 必填 | 说明                           |
| --------------- | ------ | ---- | ------------------------------ |
| `Authorization` | string | 是   | 格式固定为 `Bearer <token>`    |
| `X-User-Id`     | string | 是   | 文本传输，值必须可解析为正整数 |
| `Content-Type`  | string | 是   | 固定为 `application/json`      |

### 3.4 统一响应包裹

正式合约要求后端统一返回以下结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

字段定义：

| 字段      | 类型   | 必填 | 说明                     |
| --------- | ------ | ---- | ------------------------ |
| `code`    | number | 是   | 业务状态码，`0` 表示成功 |
| `message` | string | 是   | 提示信息                 |
| `data`    | any    | 是   | 实际业务数据             |

补充说明：

- 正式合约成功码统一使用 `0`
- 前端当前兼容 `code = 200`，但这属于兼容行为，不建议后端继续使用
- 前端历史上也兼容“非包裹裸 JSON”，但正式后端不应依赖该兼容分支

### 3.5 HTTP 状态码约定

| HTTP 状态码 | 含义             | 使用建议                             |
| ----------- | ---------------- | ------------------------------------ |
| `200`       | 请求成功         | 查询、创建、更新、删除成功时默认使用 |
| `204`       | 无响应体成功     | 仅删除接口可选，前端当前兼容         |
| `400`       | 请求参数错误     | 参数缺失、格式非法                   |
| `401`       | 未登录或登录失效 | token 缺失、token 失效               |
| `403`       | 无权限           | 预留                                 |
| `404`       | 资源不存在       | 目标记录不存在                       |
| `409`       | 资源冲突         | 例如注册时用户名已存在               |
| `422`       | 业务校验失败     | 业务规则不满足                       |
| `500`       | 服务器异常       | 未预期错误                           |

### 3.6 业务状态码约定

| code  | 含义                |
| ----- | ------------------- |
| `0`   | 成功                |
| `400` | 参数错误            |
| `401` | 未登录或 token 失效 |
| `404` | 数据不存在          |
| `409` | 资源冲突            |
| `422` | 业务校验失败        |
| `500` | 服务异常            |

### 3.7 通用字段规则

| 字段              | 类型   | 规则                                         |
| ----------------- | ------ | -------------------------------------------- |
| `date`            | string | 固定格式 `YYYY-MM-DD`                        |
| `id`              | string | 业务实体主键，除 `userId` 外统一按字符串传输 |
| `userId`          | number | 必须为正整数                                 |
| `weight`          | number | 单位 `kg`，支持小数                          |
| `calories`        | number | 单位 `kcal`，支持小数                        |
| `durationSeconds` | number | 单位秒                                       |
| `accentColor`     | string | 十六进制颜色值，如 `#0F6BFF`                 |
| `image`           | string | 可为空字符串，或资源标识 / 图片 URI          |

### 3.8 幂等与去重约定

为适配移动端“本地先写、联网后同步”的机制，后端需要满足以下要求：

1. `PUT /user-profile` 需要具备幂等性。
2. `PUT /weight-records/{date}` 需要按 `userId + date` 维度覆盖写入。
3. `POST /food-options/custom` 建议支持基于 `identityKey` 的去重 / 幂等创建。
4. `POST /workout-templates` 建议支持基于 `identityKey` 的去重 / 幂等创建。
5. 删除接口建议多次调用仍返回成功或可明确返回“已不存在”。

### 3.9 当前前端对 `data` 形态的正式要求

不同接口的 `data` 结构并不完全相同，后端需严格保持一致：

| 接口                                     | `data` 形态     |
| ---------------------------------------- | --------------- |
| `POST /auth/register`                    | 单对象          |
| `POST /auth/login`                       | 单对象          |
| `GET /user-profile`                      | 单对象          |
| `PUT /user-profile`                      | 单对象          |
| `GET /weight-records`                    | 数组            |
| `GET /weight-records/summary`            | 单对象          |
| `PUT /weight-records/{date}`             | 单对象          |
| `GET /food-options`                      | `{ items: [] }` |
| `POST /food-options/custom`              | 单对象          |
| `PUT /food-options/custom/{foodId}`      | 单对象          |
| `DELETE /food-options/custom/{foodId}`   | 空对象或空响应  |
| `GET /food-plans`                        | `{ plans: [] }` |
| `POST /food-plans`                       | 单对象          |
| `PUT /food-plans/{planId}`               | 单对象          |
| `DELETE /food-plans/{planId}`            | 空对象或空响应  |
| `GET /workout-types`                     | `{ items: [] }` |
| `GET /workout-templates`                 | `{ items: [] }` |
| `POST /workout-templates`                | 单对象          |
| `PUT /workout-templates/{templateId}`    | 单对象          |
| `DELETE /workout-templates/{templateId}` | 空对象或空响应  |
| `GET /workout-plans`                     | `{ plans: [] }` |
| `POST /workout-plans`                    | 单对象          |
| `DELETE /workout-plans/{planId}`         | 空对象或空响应  |
| `GET /workout-records`                   | `{ items: [] }` |
| `POST /workout-records`                  | 单对象          |
| `GET /workout-records/daily-summary`     | 单对象          |

兼容行为说明：

- 前端当前兼容 `GET /workout-templates` 返回 `data.templates`
- 前端当前兼容 `GET /workout-records` 返回 `data.records`
- 正式后端仍应统一返回 `items`

## 5. 认证模块

### 5.1 注册

`POST /api/v1/auth/register`

请求体：

| 字段       | 类型   | 必填 | 说明   |
| ---------- | ------ | ---- | ------ |
| `username` | string | 是   | 用户名 |
| `password` | string | 是   | 密码   |

请求示例：

```json
{
  "username": "demo",
  "password": "123456"
}
```

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "userId": 1001,
    "username": "demo",
    "token": "mock-token-1001"
  }
}
```

失败场景：

- 用户名或密码为空：`400`
- 用户名已存在：`409`

合约说明：

- 成功注册后需要直接返回可用登录态
- 前端注册成功后会立即调用 `GET /user-profile`

### 5.2 登录

`POST /api/v1/auth/login`

请求体：

| 字段       | 类型   | 必填 | 说明   |
| ---------- | ------ | ---- | ------ |
| `username` | string | 是   | 用户名 |
| `password` | string | 是   | 密码   |

请求示例：

```json
{
  "username": "demo",
  "password": "123456"
}
```

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "userId": 1001,
    "username": "demo",
    "token": "mock-token-1001"
  }
}
```

失败场景：

- 用户名或密码为空：`400`
- 用户不存在：`404`
- 密码错误：`401`

合约说明：

- `userId` 必须是正整数
- `token` 必须是非空字符串
- 前端登录成功后会立即调用 `GET /user-profile`

`PUT /api/v1/user-profile`

```json
{
  "nickname": "Julia",
  "heightCm": "168",
  "weightKg": "58.2",
  "age": "27",

}
```

```json
{
  "code": 0,
```

## 7. 体重模块

### 7.1 体重记录对象

| 字段        | 类型    | 必填 | 说明                                    |
| ----------- | ------- | ---- | --------------------------------------- |
| `id`        | string  | 是   | 记录 ID                                 |
| `date`      | string  | 是   | 日期，格式 `YYYY-MM-DD`                 |
| `weight`    | number  | 是   | 体重，单位 kg                           |
| `isUpdated` | boolean | 否   | 仅 `PUT` 返回时出现，表示是否覆盖旧记录 |

### 7.2 获取体重记录列表

`GET /api/v1/weight-records?startDate=2026-04-01&endDate=2026-04-30`

查询参数：

| 参数        | 类型   | 必填 | 说明     |
| ----------- | ------ | ---- | -------- |
| `startDate` | string | 否   | 起始日期 |
| `endDate`   | string | 否   | 结束日期 |

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": [
    {
      "id": "weight-1",
      "date": "2026-04-15",
      "weight": 58.9
    },
    {
      "id": "weight-2",
      "date": "2026-04-16",
      "weight": 58.7
    }
  ]
}
```

合约说明：

- `data` 必须是数组，不是对象包裹
- 返回结果建议按日期升序排列

### 7.3 获取体重汇总

`GET /api/v1/weight-records/summary?days=7`

查询参数：

| 参数   | 类型   | 必填 | 说明                        |
| ------ | ------ | ---- | --------------------------- |
| `days` | number | 否   | 查询最近 N 天，默认可取 `7` |

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "latestRecord": {
      "id": "weight-5",
      "date": "2026-04-19",
      "weight": 58.2
    },
    "previousRecord": {
      "id": "weight-4",
      "date": "2026-04-18",
      "weight": 58.4
    },
    "recentCount": 5,
    "averageWeight": 58.54,
    "changeInRange": -0.7,
    "changeFromPrevious": -0.2
  }
}
```

响应字段：

| 字段                 | 类型   | 必填 | 说明               |
| -------------------- | ------ | ---- | ------------------ |
| `latestRecord`       | object | 否   | 最新记录           |
| `previousRecord`     | object | 否   | 最新记录前一条     |
| `recentCount`        | number | 是   | 最近范围内记录数   |
| `averageWeight`      | number | 是   | 平均体重           |
| `changeInRange`      | number | 是   | 范围内首尾变化     |
| `changeFromPrevious` | number | 是   | 最新相对上一条变化 |

### 7.4 按日期新增或覆盖体重

`PUT /api/v1/weight-records/{date}`

请求路径示例：

`PUT /api/v1/weight-records/2026-04-22`

请求体：

| 字段     | 类型   | 必填 | 说明   |
| -------- | ------ | ---- | ------ |
| `weight` | number | 是   | 体重值 |

请求示例：

```json
{
  "weight": 58.1
}
```

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": "weight-1777020000000-123",
    "date": "2026-04-22",
    "weight": 58.1,
    "isUpdated": false
  }
}
```

合约说明：

- 唯一键建议为 `userId + date`
- 若该日期已有记录，则覆盖旧值并返回 `isUpdated: true`
- 若该日期不存在记录，则新增并返回 `isUpdated: false`

### 8.3 新增自定义食物

| 字段             | 类型   | 必填 | 说明                   |

| `image`          | string | 是   | 图片 URI 或空字符串    |

```json
{
  "identityKey": "ji-xiong-rou-juan",
```

2. 业务成功码统一使用 `code = 0`。
3. 严格保持每个接口既定的 `data` 形态。
4. 非登录接口统一支持 `Authorization` 与 `X-User-Id`。
5. 保持前端当前字段类型不变，尤其是资料对象和模板对象中的字符串数字字段。

### 12.3 同步机制相关说明

当前前端不是通过单独的“批量同步接口”与后端交互，而是采用：

1. 本地先写入
2. 将待同步操作写入同步队列
3. 联网后按顺序重放到上述业务接口

因此后端无需额外提供批量同步接口，但应尽量保证：

- 创建接口支持合理去重
- 更新接口幂等
- 删除接口重复调用不致于破坏状态

## 13. 结论

本项目正式接口风格为“前后端分离 + REST 风格路径 + 统一响应包裹 + 本地优先同步兼容”。后端若按本文约定实现，即可同时满足：

1. HarmonyOS 前端真实运行需求
2. 本地 mock 联调需求
3. 比赛材料中对系统接口设计的说明需求

如后续后端实体设计或字段命名发生调整，应优先同步更新本文，再同步修改前端请求封装与 mock 服务实现，避免文档、代码和接口三者脱节。
