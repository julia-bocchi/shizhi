# 组件图与顺序图补充说明

这批图分成三类：

- 组件图：强调 `Page -> Pack/Helper -> Storage/API`
- 部署图：强调 `Harmony App -> mock-backend -> 外部 API / 本地存储`
- 顺序图：只保留一个模块里最重要的一条主流程

## 通用后端处理骨架

`mock-backend/server.js` 的主线基本一致，画后端内部时可以复用这套结构：

1. HTTP 请求进入 `server.js`
2. `loadStore()` 读取 `mock-backend/data.json`
3. 根据路由定位当前用户与业务集合，如 `weightRecords`、`foodPlans`、`workoutRecords`
4. 查询类接口直接返回结果
5. 写入类接口更新内存对象后调用 `saveStore(store)`
6. 返回 JSON 响应给前端

## Home

组件图重点：

- `HomeTabPage.ets` 是页面入口
- `homeDashboard` 负责首页摘要计算
- `local-health-cache` 提供 `foodPlanText`、`workoutRecordText`、`weightRecordText`、`userProfileText`
- `syncCore` 不是首页主动调用的远端接口，而是其他模块同步后间接刷新首页数据

顺序图主流程：

1. 用户打开首页
2. `HomeTabPage` 读取本地缓存
3. 页面内部调用 `getCalorieSummary()`、`getWeightTrendSummary()`、`getReminderItems()`
4. 这些方法进一步调用 `getTodayDashboardCalories()`、`getHomeWeightTrend()`、`getHomeReminderItems()`
5. Helper 基于缓存计算热量摘要、体重趋势、提醒项
6. 页面渲染卡片和快捷入口

## Record

组件图重点：

- `RecordTabPage.ets` 负责录入、月历、趋势
- `recordModule` 负责本地趋势和日历计算
- `syncCore` 负责体重记录即时同步或入队
- 后端核心接口是 `GET /weight-records`、`GET /weight-records/summary`、`PUT /weight-records/{date}`

顺序图主流程：

1. 用户在 `RecordTabPage.submitWeightRecord()` 提交体重
2. 页面先做输入校验，再调用 `addOrUpdateRecord()` 覆盖本地 `weightRecordText`
3. 页面调用 `syncOperationNowOrQueue(createWeightUpsertOperation(...))`
4. `SyncService.syncWeightOperation()` 调用后端 `PUT /api/v1/weight-records/{date}`
5. 后端 `loadStore()` 后在 `user.weightRecords` 中新增或更新当日记录
6. 后端 `saveStore(store)` 持久化到 `data.json`
7. 前端用远端结果回填本地状态，更新同步提示

## Food

组件图重点：

- `FoodTabPage.ets`、`FoodPlanPage.ets`、`FoodSelectionPage.ets` 是三个主要页面
- `foodManage` 负责食物卡展示、餐次规划、推荐结果整理
- `syncCore` 负责食物卡和餐次计划同步
- 外部依赖除了后端，还有 `MediaLibraryKit` 图片选择，以及 AI 推荐接口

顺序图主流程：

1. 用户在 `FoodSelectionPage.saveTodaySelections()` 保存当天餐次
2. 页面按 `selectedDate + selectedMealType` 先剔除旧计划，再组装新的 `nextMealPlans`
3. 页面先写本地 `foodPlanText`
4. 页面调用 `syncOperationNowOrQueue(createFoodMealReplaceOperation(...))`
5. `SyncService.syncFoodMealOperation()` 先 `GET /food-plans` 拉取当天远端餐次
6. 对同日期同餐次的远端记录执行删除，再逐条 `POST /food-plans`
7. 后端在 `server.js` 中可能先 `ensureFoodOptionForPlan()`，然后 `saveStore(store)`
8. 前端用远端返回的正式 ID 替换本地临时项

## Exercise

组件图重点：

- `ExerciseTabPage.ets` 负责计划和模板管理
- `ExerciseDetailPage.ets` 负责训练中详情、计时和完成保存
- `exerciseModule` 负责训练配置、计划整理、反馈文案
- `syncCore` 负责模板、计划、训练记录同步
- 外部依赖包括训练后端接口和 AI 推荐接口

顺序图主流程：

1. 用户在 `ExerciseDetailPage.finishAndSaveSession()` 结束训练
2. 页面停止计时器，计算 `sessionCalories`、`currentMetrics`
3. 页面组装 `nextRecord`，写回本地 `workoutRecordText`
4. 页面调用 `syncOperationNowOrQueue(createWorkoutRecordCreateOperation(...))`
5. `SyncService.syncWorkoutRecordOperation()` 调用 `POST /api/v1/workout-records`
6. 后端 `loadStore()` 后把新记录插入 `user.workoutRecords`
7. 后端 `saveStore(store)` 落盘
8. 前端根据返回结果回填远端记录 ID，并返回上一页

## Assistant

组件图重点：

- `AiAssistantTabPage.ets` 是交互入口
- `assistantManage` 负责任务识别、提示词组织、结果解析
- `assistant-config-cache` 保存模型地址、密钥、历史会话
- `health-plan-cache` 提供体重、训练、饮食、计划上下文
- 外部依赖是 `BigModel Chat API`

顺序图主流程：

1. 用户在 `AiAssistantTabPage.submitToAssistant()` 发送问题
2. 页面校验输入和忙碌状态，先插入用户消息与待处理中消息
3. 页面读取 AI 配置和健康上下文
4. 页面调用 `requestAiAssistant(...)`
5. `AiAssistantHelper` 组装请求并访问第三方聊天接口
6. AI 返回文本回复以及可能的训练计划、饮食计划草案
7. 页面把结果解析成 `AiAssistantResponse`
8. 页面将会话快照写回缓存，并展示可导入内容

## Profile/Auth

组件图重点：

- `LoginPage.ets` 负责登录注册
- `ProfileTabPage.ets` 负责资料查看和编辑
- `accountManage` 聚合认证、资料读取、会话管理
- `syncCore` 负责资料更新同步
- 后端核心接口是 `POST /auth/login`、`POST /auth/register`、`GET /user-profile`、`PUT /user-profile`

顺序图主流程：

1. 用户在 `LoginPage.handleLogin()` 提交账号密码
2. 页面先校验输入，再调用 `loginWithPassword()`
3. 前端请求 `POST /api/v1/auth/login`
4. 后端校验账号密码，生成或刷新 `mock-token-{userId}`，再 `saveStore(store)`
5. 前端保存 `authSessionText`
6. 页面继续调用 `fetchUserProfile()`
7. 后端返回 `user.profile`
8. 前端写回 `userProfileText`，切到首页

补充说明：

- 如果后续还要单独补一张“资料更新”顺序图，可以从 `ProfileTabPage` 的资料保存流程展开：
  `ProfileTabPage -> syncOperationNowOrQueue(profile put) -> PUT /user-profile -> saveStore() -> 更新 userProfileText`
