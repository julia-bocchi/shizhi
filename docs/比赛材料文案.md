# 参赛材料文案

## 开源代码与组件使用情况说明

本作品核心业务功能由团队独立设计与开发完成，主要包括用户登录与资料管理、体重记录与趋势分析、饮食计划管理、训练计划管理、训练记录管理、AI 助手交互、离线缓存与同步机制等。项目未直接复制或改编其他开源项目的业务源码，未将现成开源项目整体包装后作为参赛作品提交。

在技术实现过程中，项目主要使用了 HarmonyOS 官方提供的开发框架与系统能力组件，包括 ArkTS/ArkUI 页面开发能力、网络请求能力、日志分析能力、媒体资源选择能力以及基础系统权限能力，用于实现界面构建、数据请求、日志调试、图片选择和设备交互等功能。测试阶段使用了 HarmonyOS 官方测试工具 `@ohos/hypium` 与 `@ohos/hamock` 进行基础单元测试与调试验证。

前端与后端通过标准 HTTP 接口进行通信，系统采用前后端分离设计。后端采用 `Spring Boot + MySQL` 技术方案，其中 Spring Boot 主要用于业务接口开发、系统分层组织和服务端逻辑实现，MySQL 主要用于用户账号、用户资料、体重记录、饮食计划、训练模板、训练计划、训练记录等核心业务数据的持久化存储。当前工程中保留了本地联调验证用的辅助后端脚本与数据库结构脚本，主要用于开发阶段的接口测试和原型演示，不影响作品正式后端的独立实现。

此外，作品中的 AI 助手与智能推荐能力通过标准 API 方式接入第三方大模型服务。该部分属于外部智能能力调用，不构成对外部开源业务源码的直接复用；团队主要完成了健康数据整理、提示词设计、结果解析、结构化草案生成以及与本地业务页面的导入联动等关键实现。

总体而言，本作品遵循“自主开发为主、官方组件为辅、外部能力按接口接入”的原则。所有开源组件和官方开发能力均仅作为基础开发支撑工具使用，未替代作品本身的核心算法设计、业务逻辑设计和交互流程设计。

## 设计思路

本作品面向日常健康管理场景，围绕“记录 - 分析 - 规划 - 执行 - 反馈”这一完整闭环进行设计，希望帮助用户把体重管理、饮食安排、训练执行和智能建议整合到同一应用中，降低健康管理碎片化带来的使用门槛。相比只记录数据或只提供单点建议的应用，本作品更强调数据之间的关联性和计划执行的连续性，使用户能够从静态记录逐步过渡到可执行的个性化健康管理方案。

在总体架构上，系统采用前后端分离设计。前端基于 HarmonyOS ArkTS/ArkUI 实现多页面、多模块的原生应用，负责页面展示、用户交互、本地缓存、离线编辑与同步控制；后端基于 Spring Boot 构建业务服务，基于 MySQL 完成数据持久化管理，负责用户身份管理、业务数据存储、核心业务接口提供以及后续扩展的数据分析支撑。前后端之间通过统一的 REST 风格接口进行通信，接口覆盖登录、资料、体重、饮食、训练模板、训练计划和训练记录等核心对象，便于后续扩展与维护。

在功能结构设计上，作品将系统划分为五个主要业务模块。第一是用户与资料模块，用于完成账号登录、注册和基础健康信息维护，为后续训练和饮食建议提供个体化参数。第二是体重记录模块，用于按日期记录体重，并结合近期数据生成趋势分析和变化反馈。第三是饮食管理模块，用于维护预设食物、自定义食物和每日餐次计划，使用户能够围绕早餐、午餐、晚餐和加餐进行安排。第四是训练管理模块，用于维护预设训练类型、自定义模板、训练计划和训练完成记录，支持计划生成、训练执行和结果回写。第五是 AI 助手模块，用于基于用户资料、近期体重、训练记录和现有计划，生成自然语言建议以及可直接导入的训练和饮食草案。

在交互设计上，作品强调“低门槛录入”和“结果可落地”。例如，AI 模块并不是只返回一段文本建议，而是将生成结果进一步解析为结构化训练计划和饮食计划草案，用户可以在页面中修改日期、标题、备注等信息后直接导入到对应业务页，减少从“建议”到“执行”的操作断层。训练模块支持从预设项目、已保存模板和 AI 草案三种来源生成计划；饮食模块支持在预设食物、自定义食物和 AI 推荐结果之间灵活组合，从而提高系统的可操作性和可持续使用性。

在数据管理方面，作品采用“本地优先、后台同步”的设计思路。移动端首先将用户操作写入本地持久化存储，保证在网络不稳定或后端暂时不可用时，用户仍然可以继续记录体重、编辑饮食和训练计划。系统随后通过同步队列机制将待同步数据按顺序提交至后端，并在同步成功后使用正式数据回填本地状态。该设计提升了应用在真实移动场景下的可用性，也使系统更符合随时记录、随时查看的健康管理需求。

在智能化设计方面，作品没有将 AI 作为孤立聊天功能处理，而是将其嵌入业务流程中。一方面，AI 助手会结合用户基础信息、近期体重变化、训练记录和已有计划生成更贴合用户状态的建议；另一方面，AI 输出被约束为结构化数据格式，便于系统进行解析、校验、展示与导入。这种设计兼顾了自然语言交互的灵活性和业务系统执行的确定性，使 AI 能力真正服务于健康管理流程，而不是停留在展示层面。

在可扩展性方面，作品的数据结构和接口边界划分较为清晰。数据库设计已经围绕用户账号、用户资料、体重记录、食物选项、饮食计划、训练模板、训练计划、训练记录等核心实体建立了基础表结构，为后续扩展周报统计、目标达成分析、个性化推荐优化和多端数据同步提供了良好的基础。整体上，作品兼顾了应用体验、业务完整性、技术可实现性与后续扩展空间，体现了以用户真实使用场景为导向的软件设计思路。

## 设计重点难点

### 设计重点

本作品的第一个设计重点是前后端分离架构下的系统协同设计。前端基于 HarmonyOS ArkTS/ArkUI 构建原生移动应用，后端采用 Spring Boot + MySQL 提供统一业务接口与数据存储能力。通过对用户、体重、饮食、训练、计划、记录等核心对象进行统一建模，系统形成了较为清晰的数据流转链路，为后续功能扩展和持续维护奠定了基础。

第二个设计重点是健康管理业务闭环的构建。作品并非单纯实现某一个记录功能，而是将用户资料、体重变化、饮食安排、训练计划、训练记录和 AI 建议联动起来，形成“数据采集 - 状态分析 - 方案生成 - 执行反馈 - 再次调整”的完整流程。这种闭环设计能够提升系统的实际使用价值，也更符合健康管理类应用的真实需求。

第三个设计重点是 AI 能力的业务化落地。系统没有将 AI 仅作为聊天入口，而是进一步把 AI 输出约束为可解析、可编辑、可导入的结构化结果，使其能够与训练页和饮食页直接联动。这样既保留了自然语言交互的灵活性，又保证了业务数据进入系统后的可执行性和可管理性。

第四个设计重点是移动端本地优先的数据管理策略。考虑到移动场景中网络状态并不稳定，系统将本地缓存、持久化存储和同步队列纳入整体设计，在保证用户操作实时反馈的同时，尽可能降低网络波动对使用体验的影响。这一设计使系统具备更强的连续使用能力和场景适应能力。

### 设计难点

本作品的第一个设计难点是本地数据与后端数据的一致性控制。由于系统支持本地先写入、后同步的机制，用户资料、体重记录、饮食计划、训练模板、训练计划和训练记录等数据都可能同时存在“本地临时状态”和“服务端正式状态”。如何保证同步顺序正确、失败后可重试、成功后可回填，并避免数据重复、覆盖错误或状态错乱，是系统实现中的核心难点之一。

第二个设计难点是多业务模块之间的数据联动复杂度较高。体重模块影响趋势分析，资料模块影响训练消耗估算与 AI 上下文，训练记录又会反向影响首页摘要和 AI 建议，饮食计划还需要与每日热量目标和推荐逻辑结合。各模块看似独立，实际上高度关联，因此在设计时必须兼顾模块解耦和信息共享，避免出现耦合过深或状态分散的问题。

第三个设计难点是 AI 返回结果的不确定性处理。大模型输出具有一定随机性，如果直接展示自然语言结果，虽然交互简单，但无法直接支撑业务页面使用；如果要求 AI 输出结构化内容，又必须处理字段缺失、格式不规范、语义不稳定等问题。因此，系统需要在提示词设计、结果解析、字段校验、默认值补全和导入逻辑之间建立完整机制，才能让 AI 能力稳定服务于真实业务流程。

第四个设计难点是用户体验与系统复杂度之间的平衡。健康管理应用涉及较多数据字段和业务操作，如果界面过于复杂，用户容易产生使用负担；但如果过度简化，又难以承载训练计划、饮食安排和智能建议等较复杂功能。因此，本作品在页面设计中重点强调低门槛录入、结果直接导入和关键数据可视化展示，希望在专业性与易用性之间取得平衡。

总体来看，本作品的设计重点在于构建一个面向真实健康管理场景的完整业务闭环，而设计难点则集中在跨模块数据协同、前后端状态一致性、AI 结果稳定落地以及复杂功能的易用性表达等方面。这些重点与难点共同构成了本作品的核心设计价值。
